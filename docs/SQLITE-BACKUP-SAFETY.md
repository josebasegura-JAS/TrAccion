# PR B · Backups y restauración

La copia viva y de cierre se generan exclusivamente con Online Backup API a un fichero temporal hermano del destino; se comprueba quick_check, UUID, aplicación, entorno y versión de esquema antes de rename. No hay fallback a copiar una base viva por estos caminos. Las copias derivadas y JSON se publican con temporal y rename. Si no se confirma instantánea nueva no se toca el respaldo SQLite vigente ni se distribuye un respaldo antiguo. Si falla algún destino configurado no se declara manual exitoso; se conserva la revisión pendiente. No se modifican intervalos ni retenciones. El auxiliar histórico backupSqliteDatabase sigue existiendo para otros caminos no migrados.

## Restauración
La restauración física desde Ajustes queda bloqueada incluso en producción: un lock de operación no demuestra ausencia de otros handles SMB. La restauración JSON conserva su procedimiento previo; PRUEBAS sigue bloqueando ambas. Para recuperación física, el administrador debe establecer mantenimiento fuera de la aplicación: cerrar todos los clientes y bloquear nuevas aperturas del recurso, confirmar ausencia de handles en el servidor, preservar íntegramente base y sidecars, validar una copia independiente (identidad y quick_check), restaurar y comprobar en entorno desechable antes de volver a habilitar el recurso. No existe en esta PR una herramienta automatizada de mantenimiento ni se declara validada restauración SMB. No se autoriza sustituir un archivo activo. El módulo rollback se conserva para revisión posterior.
